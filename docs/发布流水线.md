# 发布流水线

- 更新：2026-11-05
- 结论：**发布唯一入口是本地一键发布 `deploy/publish.sh`；GitHub Actions 只做构建验证，不部署。**

---

## 一、现在的走法

```
开发 → 提交推送 ──► GitHub Actions（ci.yml）：编译 + 测试 + 打包，约 2 分钟出结论
                        └── 不部署任何东西

      要发版时 ─────► bash deploy/publish.sh（本机执行）
                        └── 构建 → 备份 → 传 jar → 数据库迁移 → 发前端 → 重启 + 健康检查
                            全程约 3 分钟，失败自动回滚
```

| 动作 | 命令 | 耗时 | 费用 |
| --- | --- | --- | --- |
| 推送验证 | `git push`（自动触发 CI） | 约 2 分钟 | 0（公开仓库 Actions 免费） |
| 发布上线 | `bash deploy/publish.sh` | 约 3 分钟 | 0 |
| 发布自检（不部署） | `bash deploy/publish.sh --build-only` | 约 1 分钟 | 0 |
| 应急跳过测试 | `SKIP_TESTS=1 bash deploy/publish.sh` | 约 1 分钟 | 0 |

## 二、为什么不在 GitHub Actions 里部署（实测数据）

对同一条「构建 → 发布到生产」链路做过对比实测（2026-11-05）：

| 路径 | 全程耗时 | 费用 | 结论 |
| --- | --- | --- | --- |
| 本地 `publish.sh`（本机→服务器，同国链路） | **约 3 分钟** | 0 | ✅ 采用 |
| 旧方案：COS 中转（runner→腾讯云→服务器） | 1m59s ~ 3m09s | **按流量计费** | 弃用（不想花钱） |
| GitHub runner scp 直传服务器（跨境） | **25~30 分钟** | 0 | ❌ 弃用 |

跨境 scp 被限速实测 **~40KB/s**：44MB 的 jar 传了 20+ 分钟才到 82%。这不是配置问题，
是「海外 runner → 国内服务器」的链路质量决定的——当年做 COS 中转（全球加速 + 服务器内网拉取）
就是为了绕开它。既然要零费用，就把部署挪到本机（本机在国内，同国传输 44MB 只要几秒）。

## 三、本地一键发布：deploy/publish.sh

### 用法

```bash
bash deploy/publish.sh              # 完整发布
bash deploy/publish.sh --build-only # 只构建，不碰服务器
SKIP_TESTS=1 bash deploy/publish.sh # 应急跳过验证（显式启用，记录进发布结果）
```

### 配置

优先级：环境变量 > `deploy/.deploy.env`（已 gitignore，勿提交）> 默认值。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DEPLOY_HOST` | （必填） | 服务器 IP，如 `140.143.166.155` |
| `DEPLOY_PORT` | `22` | SSH 端口 |
| `DEPLOY_USER` | `ubuntu` | SSH 用户 |
| `SSH_KEY` | `~/.ssh/travel_os_deploy` | 部署私钥（初始化手册生成的那把） |
| `MAVEN_BIN` | Maven 3.9.11 路径 | **勿用 3.6.3**（有 `-source 8` 内插 bug） |
| `JAVA_HOME` | JDK 17 路径 | — |
| `NODE_BIN` | 本机托管 node 路径 | 前端测试用；缺失时回退 PATH 上的 `node` |
| `RELEASE_ID` | 时间+源码短 SHA | 发布版本标识；勿手工指定（重放/模拟测试可覆盖） |

### 发布状态机：八个阶段与失败行为（v2，2026-11-21）

每次发布生成唯一 **RELEASE_ID**（时间+git 短 SHA），写入三处并在验证时强制一致：
`/opt/travel-os/release.env`（restart 时注入新 JAR 进程 → `/api/health` 的 `release` 字段）、
前端包内 `release.json`（nginx 按 `:8082/release.json` 直接服务）、
`/opt/travel-os/current-release.txt`（当前版本记录）。

| 阶段 | 内容 | 失败行为 |
| --- | --- | --- |
| S1 预检+验证 | 工具/私钥/本地磁盘≥2GB → 前端测试（通知流+AI 策略+文档预览+分类回归）→ `mvn -B verify`；服务器磁盘≥2GB、目录可写、发布锁空闲 | **中止，服务器任何文件未动** |
| S2 staging 上传 | jar/www tar（内含 release.json）/SHA256SUMS/verify.sh → 服务器 staging，`sha256sum -c` 校验 | 中止；线上未动（staging 残留下次覆盖） |
| S3 备份 | 备份当前 jar/www/上一版本 ID 到 `/opt/travel-os/backups/`（保留 3 份，只动本项目备份路径），**完成后才允许覆盖**；记录 HAS_PREVIOUS | ERR 陷阱中止；线上未动 |
| S4 数据库迁移 | 按文件名序全量重放（服务器 flock 内，`ON_ERROR_STOP=1`） | 中止；**线上仍是上一版本组合**；已执行部分靠幂等重放（非事务回滚），修复后直接重跑发布 |
| S5 切换 | 同一 flock 内：systemd unit + release.env → 原子替换 jar → rsync 前端（`--delete`，保留 `/ci/`）→ current-release.txt → restart | 失败/中断 → **自动回滚**（恢复同一次备份的 jar+前端+release.env）→ 重新验证 |
| S6 验证 | 服务器本地轮询 12×5s：`/api/health`（服务标识+`release`=目标）+ `/api/health/ready`（200=库可连+关键结构齐）+ `:8082/release.json`（release=目标） | 未通过 → **自动回滚**并重新验证 |
| S7 回滚 | 恢复上一版本组合 → restart → 再验证（`release`=上一版本 + 就绪 200） | 回滚也失败 → 打印人工恢复信息（备份路径/当前版本/命令）→ 退出 1，**绝不误报成功** |
| S8 完成 | 输出发布结果（release/源码/validation/jar sha256/回滚点） | — |

- **SKIP_TESTS=1 应急通道**：显式设置才生效；跳过测试并以 `validation: skipped` 记入
  release.json 与发布结果汇总，输出清晰提示。
- **发布互斥**：本地 `deploy/.publish.lock`（进程锁）+ 服务器 `flock /opt/travel-os/publish.lock`
  （迁移与切换段），并发发布直接失败。
- **发布成功的判定条件**：S1–S6 全部通过——即三处版本标识一致（运行中 JAR 的 health `release`
  = 目标 = 前端 release.json）、就绪检查 200、服务标识为 travel-os-api；仅“进程存在”不算成功。
- **可用性边界（如实声明）**：单机无原子切换——S5 重启窗口（数秒）内前端静态页可访问、API
  短暂不可用；若本机/连接在 S5 中途断开，远端可能停在半切换状态，按下方「人工回滚」处理。

### 数据库迁移与回滚边界（发布前必读）

- 迁移**必须与上一应用版本向后兼容**，采用「先扩展 → 后迁移 → 最后清理」：
  新 JAR 只依赖已存在的结构；旧 JAR 能在新结构上继续运行（至少覆盖一次发布周期）。
- 幂等重放 **不是** 事务回滚：迁移部分完成时，已执行语句不撤销（数据保留），修复后重放即可；
  迁移失败时线上仍是上一版本组合，可安全重跑发布。
- **不能由脚本自动证明的兼容性（发布前人工评审）**：删除/重命名列、新增 NOT NULL 无默认、
  收窄列类型、删除枚举值、收紧约束——这类变更会让旧 JAR 在迁移后立即出错，必须拆成多次
  发布（先双写/兼容视图，确认旧版本退役后再清理）。
- **不自动执行破坏性反向迁移**，也不用备份自动覆盖生产数据库。
- **备份与恢复职责**：数据库备份（发布前 `pg_dump`）与上传文件（`/var/www/travel-os` 之外的
  上传目录）由运维在发布前自行备份；publish.sh 只备份应用产物（jar/前端），**应用回滚不替代
  数据恢复**。

### 人工回滚（publish.sh 回滚也失败时）

```bash
# 1) 确认现场：当前版本记录与备份清单
cat /opt/travel-os/current-release.txt
ls -1t /opt/travel-os/backups/ | head
# 2) 恢复 JAR + 前端（同一备份戳 TS，前后端必须同批恢复）
TS=<发布输出中的备份戳>
sudo cp /opt/travel-os/backups/travel-os-api.jar.bak-$TS /opt/travel-os/travel-os-api.jar
rm -rf /tmp/web-restore && mkdir -p /tmp/web-restore
tar xzf /opt/travel-os/backups/www.bak-$TS.tar.gz -C /tmp/web-restore
sudo rsync -a --delete --exclude "/ci/" /tmp/web-restore/ /var/www/travel-os/
printf 'TRAVELOS_RELEASE_ID=<上一版本ID>\n' | sudo tee /opt/travel-os/release.env
sudo systemctl restart travel-os-api
# 3) 重新验证：/api/health（标识+版本）、/api/health/ready（200）、:8082/release.json
# 数据库不回滚：结构由向后兼容保证旧 JAR 可运行；数据问题另行按 pg_dump 恢复流程处理。
```

## 四、GitHub Actions（ci.yml）

- 触发：push 到 main / PR / 手动
- 内容：Temurin JDK 17 + Maven 依赖缓存，`mvn -B verify`，**无部署、无 artifact 上传**
- 并发保护：同一分支连推只跑最新一次（cancel-in-progress）
- 历史遗留的 `SSH_*` / `TENCENT_*` Secrets 已无引用，可在仓库 Settings 清理

## 五、演进历史

1. **COS 中转时代**（~2026-11-03 前）：Actions 部署，jar 经腾讯云 COS 全球加速中转、
   服务器内网拉取（<1s），全程 2~3 分钟——快但按流量付费。
2. **scp 直传时代**（2026-11-05 上午）：去 COS 改 runner scp 直传，零费用但跨境限速 ~40KB/s，
   实测一次要 25~30 分钟，弃用。
3. **现在**：部署完全下放到本地 `publish.sh`，Actions 只做构建验证。

## 六、服务器侧备忘

- 应用：`/opt/travel-os/travel-os-api.jar`，systemd 服务名 `travel-os-api`，健康检查 `http://127.0.0.1:3001/api/health`（APP_PORT=3001；3000 已是 monevo-nginx，2026-11-20 修正）
- **Nginx**：对外监听 **8082**（80 归其他项目整合页），`/api/` 与 `/files/` 反代 `127.0.0.1:3001`（配置模板 `deploy/nginx/travel-os.conf`，已与生产一致，含生产端口无需再改）。
  **publish.sh 六阶段不含 Nginx 步骤**——conf 变更不会随发布自动生效，须按《服务器初始化手册》第七节手动应用：`cp`（或增量 `vi`）→ `nginx -t` → `systemctl reload nginx`
- 前端：`/var/www/travel-os/`（nginx），其中 `/ci/` 为历史运行状态页（已无写入方，可留可删）
- 数据库：docker 容器 `travel-os-postgres`，迁移用 `psql -U travel_os -d travel_os`
- 回滚：手动执行 `cp /opt/travel-os/backups/travel-os-api.jar.bak-<TS> /opt/travel-os/travel-os-api.jar && sudo systemctl restart travel-os-api`
