# 发布流水线

- 更新：2026-11-05
- 结论：**发布唯一入口是本地一键发布 `deploy/publish.sh`；GitHub Actions 只做构建验证，不部署。**

---

## 一、现在的走法

```
开发 → 提交推送 ──► GitHub Actions（ci.yml）：编译 + 测试 + 打包，约 2 分钟出结论
                        └── 不部署任何东西

      要发版时 ─────► bash deploy/publish.sh（本机执行）
                        └── 构建 → 备份 → 传 jar → 数据库迁移 → 发前端 → 重启 + 健康检查
                            全程约 3 分钟，失败自动回滚
```

| 动作 | 命令 | 耗时 | 费用 |
| --- | --- | --- | --- |
| 推送验证 | `git push`（自动触发 CI） | 约 2 分钟 | 0（公开仓库 Actions 免费） |
| 发布上线 | `bash deploy/publish.sh` | 约 3 分钟 | 0 |
| 发布自检（不部署） | `bash deploy/publish.sh --build-only` | 约 1 分钟 | 0 |
| 应急跳过测试 | `SKIP_TESTS=1 bash deploy/publish.sh` | 约 1 分钟 | 0 |

## 二、为什么不在 GitHub Actions 里部署（实测数据）

对同一条「构建 → 发布到生产」链路做过对比实测（2026-11-05）：

| 路径 | 全程耗时 | 费用 | 结论 |
| --- | --- | --- | --- |
| 本地 `publish.sh`（本机→服务器，同国链路） | **约 3 分钟** | 0 | ✅ 采用 |
| 旧方案：COS 中转（runner→腾讯云→服务器） | 1m59s ~ 3m09s | **按流量计费** | 弃用（不想花钱） |
| GitHub runner scp 直传服务器（跨境） | **25~30 分钟** | 0 | ❌ 弃用 |

跨境 scp 被限速实测 **~40KB/s**：44MB 的 jar 传了 20+ 分钟才到 82%。这不是配置问题，
是「海外 runner → 国内服务器」的链路质量决定的——当年做 COS 中转（全球加速 + 服务器内网拉取）
就是为了绕开它。既然要零费用，就把部署挪到本机（本机在国内，同国传输 44MB 只要几秒）。

## 三、本地一键发布：deploy/publish.sh

### 用法

```bash
bash deploy/publish.sh              # 完整发布
bash deploy/publish.sh --build-only # 只构建，不碰服务器
SKIP_TESTS=1 bash deploy/publish.sh # 跳过测试（应急）
```

### 配置

优先级：环境变量 > `deploy/.deploy.env`（已 gitignore，勿提交）> 默认值。

| 变量 | 默认值 | 说明 |
| --- | --- | --- |
| `DEPLOY_HOST` | （必填） | 服务器 IP，如 `140.143.166.155` |
| `DEPLOY_PORT` | `22` | SSH 端口 |
| `DEPLOY_USER` | `ubuntu` | SSH 用户 |
| `SSH_KEY` | `~/.ssh/travel_os_deploy` | 部署私钥（初始化手册生成的那把） |
| `MAVEN_BIN` | Maven 3.9.11 路径 | **勿用 3.6.3**（有 `-source 8` 内插 bug） |
| `JAVA_HOME` | JDK 17 路径 | — |

### 六个阶段（全部与原 CI 部署段同构）

1. **构建**：`mvn -B verify`（编译 + 测试 + 打包）；若本地 3001 开发服务占用 jar 会先自动停掉
2. **备份**：服务器现有 jar 与前端各备份一份（保留最近 3 份，`/opt/travel-os/backups/`）
3. **传 jar**：scp 直传 → 原子替换 `/opt/travel-os/travel-os-api.jar`
4. **数据库迁移**：按文件名顺序重放 `apps/server/db/migration/*.sql`（全部幂等，已应用的自动跳过）
5. **发前端**：tar + scp → 服务器端 `rsync -a --delete` 到 `/var/www/travel-os/`（保留 `/ci/` 状态页）
6. **重启 + 健康检查**：`systemctl restart travel-os-api`，轮询 `/api/health`（5s×12）；
   **失败自动回滚**到最近备份并重启

成功标志：末行输出「health check OK / 发布完成：http://<IP>/」。

## 四、GitHub Actions（ci.yml）

- 触发：push 到 main / PR / 手动
- 内容：Temurin JDK 17 + Maven 依赖缓存，`mvn -B verify`，**无部署、无 artifact 上传**
- 并发保护：同一分支连推只跑最新一次（cancel-in-progress）
- 历史遗留的 `SSH_*` / `TENCENT_*` Secrets 已无引用，可在仓库 Settings 清理

## 五、演进历史

1. **COS 中转时代**（~2026-11-03 前）：Actions 部署，jar 经腾讯云 COS 全球加速中转、
   服务器内网拉取（<1s），全程 2~3 分钟——快但按流量付费。
2. **scp 直传时代**（2026-11-05 上午）：去 COS 改 runner scp 直传，零费用但跨境限速 ~40KB/s，
   实测一次要 25~30 分钟，弃用。
3. **现在**：部署完全下放到本地 `publish.sh`，Actions 只做构建验证。

## 六、服务器侧备忘

- 应用：`/opt/travel-os/travel-os-api.jar`，systemd 服务名 `travel-os-api`，健康检查 `http://127.0.0.1:3000/api/health`
- 前端：`/var/www/travel-os/`（nginx），其中 `/ci/` 为历史运行状态页（已无写入方，可留可删）
- 数据库：docker 容器 `travel-os-postgres`，迁移用 `psql -U travel_os -d travel_os`
- 回滚：手动执行 `cp /opt/travel-os/backups/travel-os-api.jar.bak-<TS> /opt/travel-os/travel-os-api.jar && sudo systemctl restart travel-os-api`
