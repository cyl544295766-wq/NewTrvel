```text
- Travel OS Java 后端：127.0.0.1:3001。

- deploy/nginx/travel-os.conf 中 /api/、/files/ 仍代理到 3000。

  - 普通静态资源仍能访问。

- 无法执行的检查明确标注“未执行”及原因。
- 仅修改配置和文档时，不运行无关的后端全量测试。

操作边界：

完成后报告：
```

```text
CI 仅设置 Java 并执行 mvn -B verify，但后端集成测试已经依赖真实 PostgreSQL。工作流没有准备数据库和迁移，也没有运行现有前端测试，无法可靠复现本地验收结果。

一、准备独立的 CI 数据库

1. 使用 GitHub Actions PostgreSQL 16 service，配置健康检查和有界等待。

5. 按项目约定顺序执行全部迁移，任何 SQL 失败必须让工作流失败。
6. 保持迁移只增不改、幂等的约定，不修改历史迁移来迁就 CI。
7. 不把整个迁移集强行包进单个事务；遵守现有 PostgreSQL 枚举等迁移限制。

二、运行后端验证

1. 使用 JDK 17、Maven 3.9.11，确保实际版本符合项目约定。

4. AI 测试使用现有模拟模型，不需要真实模型密钥或付费调用。
5. 检查测试所需的认证、种子账户、文件目录等配置，采用 CI 专用安全值。
6. 文件输出写入 CI 临时或工作目录，不依赖 Windows 个人路径。
7. Linux 与 Windows 的有效测试覆盖差异如实记录，不为了保持相同跳过数而跳过测试。
8. 若发现环境之外的真实缺陷，明确定位，只做必要修复，不扩大业务重构。

三、接入前端测试

1. 盘点 apps/web/tests 中现有测试入口，运行全部适合无浏览器环境的测试。
2. 至少覆盖现有通知流、AI 发送策略和文档预览测试。
3. 接入 E2E 错误分类模块的纯分类回归，调用实际使用的
   tools/e2e/lib/error-classify.cjs，不复制分类实现自证。
4. 如 selftest-map-classify.cjs 目前把纯分类回归与浏览器故障注入绑定，
   可最小拆分入口或增加明确的纯分类运行模式，保留原完整自检能力。
5. 纯分类模式不得启动浏览器、注册账号、连接数据库或访问地图服务。
6. 不将依赖真实高德服务的完整地图 E2E 强制塞入本轮常规 CI。
7. 不引入前端构建框架，不改变零构建部署方式，不进行无关依赖升级。

四、完善工作流结果与诊断

1. 保留 push、pull_request、手动触发及现有并发取消策略。
2. 为数据库等待、作业及必要步骤设置合理超时。
3. 后端和前端测试失败均应正确影响最终工作流状态。
4. 即使测试失败，也收集可用的 Surefire 报告和必要日志。
5. 明确产物保留期限，不上传 .env、令牌、密钥、个人文件或运行数据目录。
6. 更新测试说明，写清 CI 实际执行范围、配置来源及本地复现方式。
7. 不将“YAML 已配置”表述为“GitHub Actions 已实际通过”。

五、验证要求

- 检查工作流语法和配置引用。
- 核对 CI 使用的是临时数据库，不是生产数据库。

- 不通过删测试、放宽断言、关闭数据库约束或容忍失败来获得通过。

- 若尚未运行真实 GitHub Actions，明确留下待推送后验证的事项。

操作边界：
- 不连接生产服务器，不部署。
- 不提交、不推送，不自行触发远程工作流。
```

## 3 完善发布检查与回滚机制

```text
请完善 Travel OS 的发布检查与回滚机制，确保发布失败时能够恢复一致的前后端版本。

项目位置：D:\myWork\NewTrevl
交接文档：D:\myWork\newTrevl.md

先阅读项目约定及以下文件：
- deploy/publish.sh
- deploy/systemd/travel-os-api.service
- deploy/nginx/travel-os.conf
- deploy/app.env.example
- deploy/服务器初始化手册.md
- docs/发布流水线.md
- apps/server/src/main/java/com/travelos/controller/HealthController.java
- 数据库迁移说明及相关测试

保留当前工作区全部已有改动，尤其保留此前端口统一和 CI 改造成果。

已发现的问题：
1. 发布构建使用 -DskipTests，缺少可靠的发布前验证。
2. 发布检查主要确认 /api/health 返回服务标识，无法充分证明数据库和必要结构已就绪。
3. 发布失败时只恢复 JAR，前端可能仍为新版本。
4. 数据库已迁移后，旧 JAR 是否兼容缺少明确约束。
5. 迁移、上传、前端同步等中间阶段失败，未形成完整恢复闭环。

本任务目标：
建立清晰、可验证的发布状态与恢复流程。任何阶段失败，都不能误报成功或留下无法解释的版本组合。

一、发布前检查

1. 正常发布默认执行后端 mvn -B verify，以及适合本地运行的现有前端测试。
2. 不重复运行依赖真实地图服务的完整 E2E 作为每次发布的硬性前置。
3. 如保留应急跳过验证的入口，必须显式启用，默认关闭，输出清晰提示并记录在发布结果中。
4. 使用项目约定的工具版本；不依赖未经说明的个人路径。
5. 发布前检查必要配置、工具、目录权限和磁盘空间，失败尽量发生在修改线上文件之前。
6. 本地构建失败不得继续上传或修改服务器。
7. 保留现有端口约定：Travel OS 后端 3001、生产 Nginx 对外 8082。

二、增加明确的就绪检查

1. 保留现有存活检查，增加或完善可用于发布验收的就绪检查。
2. 至少验证数据库可连接，以及本版本运行所需的关键表和列存在。
3. 数据库不可用或结构不满足要求时，返回非成功 HTTP 状态码，例如 503；不能只在 HTTP 200 的 JSON 中写 error。
4. 响应不泄露数据库连接串、账号、密码、SQL 或内部异常详情。
5. 明确检查的能力边界，不把简单 SELECT 1 描述为完整业务健康验证。
6. 就绪检查使用有界超时与重试。
7. 为正常、数据库失败和结构缺失场景补充必要测试。
8. 发布脚本必须校验服务标识及就绪结果，避免误命中同机其他项目。

三、保证前后端版本一致

1. 为一次发布建立唯一版本标识，记录对应源码版本、构建结果及必要校验信息。
2. 在完成备份前，不覆盖当前运行产物。
3. 采用适合当前单机部署的简单方案，让 JAR 与静态前端作为同一发布版本管理。
4. 保留 /ci/ 等现有明确约定的目录，不误删上传文件、配置或用户数据。
5. 发布成功后核对实际运行版本与目标版本，不仅确认进程存在。
6. 避免并发发布互相覆盖；增加必要的发布互斥。
7. 不引入外购服务，不重构成复杂的平台系统。

四、完善失败恢复

1. 梳理构建、备份、上传、迁移、前端切换、后端启动、就绪检查各阶段的失败行为。
2. 失败时根据实际完成阶段恢复，不能盲目假定所有备份和新产物都存在。
3. 如前端与后端已经切换，恢复同一上一版本的两类产物。
4. 恢复后重新验证就绪状态及版本。
5. 回滚失败必须明确报错，输出人工恢复所需的信息，不能声称回滚成功。
6. 首次部署没有上一版本时，应安全失败并给出准确说明。
7. 增加中断处理，但不承诺无法保证的完全原子切换；明确单进程重启期间的可用性边界。
8. 备份保留与旧版本清理只能针对本项目已确认的路径，不删除当前版本、回滚目标或用户数据。

五、明确数据库迁移与回滚边界

1. 保持迁移按项目约定执行，任何 SQL 错误立即停止发布。
2. 不自动执行破坏性的数据库反向迁移，不默认用旧备份覆盖生产数据库。
3. 明确要求发布迁移与上一应用版本向后兼容，采用先扩展、后迁移、最后清理的方式。
4. 针对迁移部分完成的情况说明恢复策略；不能把幂等重放等同于事务回滚。
5. 对无法由脚本自动证明的兼容性，如实说明需要评审的内容，不提供虚假的自动保障。
6. 写清数据库及上传文件的备份、恢复职责；应用版本回滚不能替代数据恢复。

六、测试与验证

1. 检查 shell 语法。
2. 在本地临时目录、模拟 SSH/传输/服务命令或隔离环境中验证发布状态机，不操作生产。
3. 至少覆盖：
   - 正常发布。
   - 发布前验证失败。
   - 上传失败。
   - 迁移失败或部分完成。
   - 前端切换后后端启动失败。
   - 就绪检查失败。
   - 前后端恢复成功。
   - 回滚失败。
   - 首次部署无旧版本。
   - 并发发布被拒绝。
4. 验证失败场景退出码非零，且不会误打印发布成功。
5. 后端新增逻辑先运行相关测试，再运行 mvn -B verify；保留测试 Hikari 配置。
6. 不通过删除测试、放宽断言或忽略命令错误获得通过。
7. 无法执行的检查明确标注“未执行”及原因。

操作边界：
- 本任务仅完成本地实现、模拟验证和文档更新。
- 不连接生产服务器，不部署、不重启、不重载生产服务。
- 不停止已有本地开发服务。
- 不提交、不推送。
- 不顺手修改无关业务模块或升级框架。

完成后报告：
1. 修改文件及发布流程变化。
2. 发布成功的判定条件。
3. 各阶段失败后的处理表。
4. 前后端一致性和数据库兼容性的实际保障边界。
5. 自动验证结果与未执行项。
6. 生产应用步骤、人工回滚命令及首次部署注意事项。
```

## 4 优化统计接口批量查询

```text
请优化 Travel OS 统计接口的数据库查询效率，保持现有统计结果、权限和响应契约兼容。

项目位置：D:\myWork\NewTrevl

先阅读项目约定、交接文档及相关代码：
- service/TravelStatsService.java

- service/TripExpenseService.java 中结算计算逻辑

已发现的查询问题：
1. findTripsForUser() 按每个行程分别读取行程、行程天和费用。
2. 结算建议按每笔费用分别读取分摊记录。
3. memberNames() 按每个成员分别读取用户。
4. 部分按年份统计的入口先读取全部数据，再在内存筛选。

一、先记录基线

1. 梳理受影响接口及调用链，列出逐条查询的位置。
2. 在独立测试数据中记录优化前的查询次数、响应结果和耗时。
3. 至少覆盖少量行程与多行程、多费用、多成员场景。
4. 使用相同数据与测量方法对比，不将不同环境或网络波动造成的差异当作优化成果。
5. SQL 统计限定到目标请求或服务调用，排除夹具创建、启动和清理。
6. 不在日志中输出个人资料、令牌、凭证或完整敏感业务数据。

1. 批量加载当前用户可访问且未删除的行程。
2. 批量读取相关行程天、费用，再按行程 ID 分组。
3. 结算建议批量读取相关费用分摊，按费用 ID 分组。
4. 批量读取成员与用户展示信息，避免成员循环中的 selectById。

5. 保持费用分摊、结算方向、转账建议和尾差处理一致。

- 已删除、归档和不可访问行程。
- 成员权限撤销后数据不再计入。

- 已有结算建议的金额、方向和稳定性。

性能验收要求：

3. 耗时比较采用多次测量并说明数据规模，避免只挑最快结果。
4. 在可接受数据规模下检查响应时间和内存开销，不以大量全量加载换取表面上的 SQL 数量下降。
5. 不把没有实际执行的性能测试描述为已完成。
```
