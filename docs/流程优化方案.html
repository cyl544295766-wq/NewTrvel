01运行架构与流程全景

后端既是 API 又是静态服务器，同源部署无跨域；JWT 双通道（Bearer 优先、Cookie 回落）；MyBatis-Plus 行级数据权限 + 行程四角色（owner/admin/member/viewer）。文档体系完备，docs/architecture/未接入清单.md 是现成的断链台账。

旅程链路状态
J1 注册登录login → /auth/register|login → JWT → home（/dashboard 聚合）通
J2 行程 CRUDtrip-form → /trips → trips 列表 → trip-detail（枢纽）→ 8 磁贴通
J3 行程规划itinerary（天/地点/换天/排序/编辑锁）+ map + packing通联想未接 UI
J4 预订凭证bookings CRUD → vouchers（实时聚合，自动生成）凭证页无入口
J5 费用结算expenses（三分摊）→ settlement 确认 → 快照+全员通知预订不转费用
J6 记录沉淀photos（data URL）+ journals → journal-detail（编辑锁）通
J7 社交friends（搜索/添加/私信）+ square（公开/好友攻略、复制）无同意流程
J8 管理admin（概览/用户禁用/CI 状态），requireSuperAdmin 兜底通

J10 统计stats 六接口，按"参与的全部行程"口径硬编码 CNY

02瓶颈归因（22 项问题五类归因）

A · 断点（5 项）—— 链路存在但用户走不进去
  • #1 凭证页几乎无入口（最高优先）：trip-detail 8 磁贴没有"凭证"（trip-detail/index.html L829-836），bookings 页也无任何链接指向 vouchers。唯一入口藏在预订提醒通知的 staticLink 里——功能做得好（凭证=bookings 实时聚合，自动生成），但用户发现不了。
  • #2 地点联想未接 UI：后端 GET /api/places/suggestions（高德 Web Key）实测可用，itinerary 添加地点仍是纯手输。
  • #3 通知无单条删除：只有 clear-read，历史通知无法逐条清理。
  • #4 好友无"接受/拒绝"：user_friends 单向记录，A 加 B 只算"已发送"，互加全靠对方主动撞见，且加好友后对方零通知。
  • #5 数据导入缺失：账户页有导出 JSON，导入按钮存在但禁用、后端无接口。
B · 返工（5 项）—— 同一数据多处维护 / 重复建设
  • #6 预订→费用不流转：bookings.amount 记过，实际花费还要在 expenses 再录一笔；预算对比只用"预估占用"桥接（booking 金额直接拼进 getBudget），"预估→实付"无核销动作。用户视角是同一笔钱录两次。
  • #7 两套预算并行：trips.budget（总预算）与 trip_budgets（类别预算）无勾稽关系，容易对不上。
  • #8 冗余路由 3 个：GET /trips/{id}/budget 与 /expenses/budget 同 service；weather 单日端点前端有意不接。
  • #9 两套编辑锁表：journal_edit_locks 与 edit_locks（天级）结构相似分表而建。
  • #10 二维码是假的：assets/js/qr.js 自绘 finder+伪随机点，扫不出数据——现场值机/入住场景不可用，凭证页的实用价值被腰斩。
C · 等待（3 项）—— 依赖异步但未闭环
  • #11 外部依赖静默降级：LLM 三元组未配则 AI 整体不可用、高德 Key 缺失联想 503，均无强提示。
  • #12 通知无实时性：无 WebSocket/SSE，预订/天气提醒靠定时器写库，用户须刷新才看到。
  • #13 路线规划失败静默回落：map 页驾车路线失败仅 routeNotice 轻提示，成败口径不显性。
D · 口径（3 项）
  • #14 统计硬编码 CNY：bookings 支持任意币种，但统计/结算按 CNY 直加（TravelStatsService 的 PRIMARY_CURRENCY），外币花费直接失真。
  • #15 通知分页 total 会变小：过滤已过期行导致 total 与表内行数不一致，前端按 total 翻页会跳变（api-design.md 已自述）。
  • #16 角色命名两套：行程 owner/admin/member/viewer vs 平台 user/super_admin；admin 页硬编码 role!=="super_admin"，后端扩展角色会漏判。
E · 安全（6 项）
  • #17 JWT 不可吊销：logout 只清 Cookie，改密不强制下线，无 refresh/blacklist，泄露后 7 天窗口无法作废。
  • #18 CORS 过宽：allowedOriginPatterns * + allowCredentials(true)。
  • #19 secure-cookie=false 且部署模板缺该变量。
  • #20 页面骨架无服务端鉴权：数据靠 API 401 兜底，admin 入口仅 CSS 隐藏（后端有兜底，风险可控）。
  • #21 文件以 data URL 入库：照片/证件 base64 直存 PostgreSQL，无对象存储分离，500 张/行程上限下压力可观。
  • #22 种子管理员弱口令 admin123 且每次启动重置。

03优化方案：四阶段实施

顺序：先补入口（用户找得到）→ 再通流转（数据自己跑）→ 然后治理横切风险 → 最后做架构升级。每阶段独立可验收，并可直接登记进 docs/architecture/未接入清单.md。

P0 · 补断点入口（约 1 天，全部是前端 + 一两个轻端点）
  • 凭证入口 ×2：trip-detail 模块数组加入 vouchers 磁贴（第 9 格，或并入 bookings 磁贴副链接）；bookings 页头部加「🎫 我的凭证」按钮链到 /vouchers/?trip=。
  • 好友请求闭环：加好友时向对方发 notifications（type=friend_request，metadata 带 fromUserId）；friends 页区分「已发送/待对方确认/已是好友」三态；后端补 POST /api/friends/{id}/accept（互加成功才成为好友，向双方发通知）。保持 user_friends 表结构不变即可实现。
  • 通知单条删除：后端补 DELETE /api/notifications/{id}（校验 recipient），通知页操作区加删除。
  • 地点联想接 UI：itinerary「添加地点」输入框接 GET /api/places/suggestions，防抖 300ms 下拉选择，回填地名+经纬度（trip_places 已有坐标字段）。
  • 外部依赖显性提示：AI 抽屉与联想接口 503/降级时给出「服务未配置」的明确空态，不再静默。
P1 · 数据自动流转，消灭双录（2–3 天）
  • 预订→费用一键核销：bookings 卡片加「转为费用」——POST expenses 自动带金额/类别映射（flight→交通、hotel→住宿、ticket→门票）/日期（出发日）/分摊默认均分，并在 booking 上记 expense_id；已核销的预订显示「已入账」徽标且不再计入"预估占用"（消除 getBudget 的双算）。"实付与预付差额"可后续做补差编辑。
  • 预算归一：确立 trips.budget 为总预算唯一来源，expenses 页"类别预算"改为总预算的分项视图（trip_budgets 行在保存时校验 Σ类别 ≤ 总预算，超额给提示），消除两套预算打架。
  • 真二维码：凭证页改用真实二维码（值机码/订单号文本，或 booking.attachment_url 里的原始二维码图），优先方案：bookings 上传附件时保留原始二维码图并在 vouchers 页直接展示原图；无附件时退化为文本码并明确标注「示例码，不可扫描」。
  • 清理冗余：下线 GET /trips/{id}/budget 与单日 weather 端点（前端已确认不接）；edit_locks 与 journal_edit_locks 合并为一张表（加 scope 列），迁移脚本按项目惯例写成幂等 SQL。
P2 · 横切治理：口径与安全（2–3 天）
  • JWT 可吊销：最小方案——users 表加 token_valid_after 时间戳，改密/注销/禁用时刷新该值，AuthInterceptor 校验 iat ≥ token_valid_after；logout 后续可加短期黑名单（Redis 可选）。改密强制其他设备下线随之成立。
  • CORS 收紧：allowedOriginPatterns 由 * 改为配置白名单（app.env 注入），生产关闭 allowCredentials 或固定域名。
  • Cookie 安全：secure-cookie 生产强制 true（app.env.example 补变量），部署清单加检查项。
  • 币种口径：短期——统计接口按 currency 分组返回，非 CNY 标注"原币"；中期——引入汇率表（手动汇率即可起步），结算与年度统计统一折算，前端明确标注折算口径。
  • 通知分页口径：total 改为过滤后计数或响应加 totalUnfiltered，前端按返回 total 翻页。
  • admin 前后端口径统一：admin 页改为读 /auth/me 的 role 判断，删掉硬编码字符串比较。
  • 种子口令：SeedRunner 仅在 admin 密码为默认值且非首次启动时告警；start.cmd 不再回显密码；生产部署强制改密。
P3 · 架构升级（按 roadmap 排期）
  • 文件出库：照片/证件从 data URL 迁到对象存储（本地磁盘目录起步即可：后端提供 /api/files/* 静态映射 + 上传接口），DB 只存 URL——容量、备份、内存压力同时解决。
  • 通知实时化：Web 端 SSE（Spring SseEmitter）推送未读数变化，比 WebSocket 成本低；预订提醒触发时可即时送达。
  • 数据导入：与导出对称的 POST /api/account/import（JSON 校验 + 冲突策略：跳过/覆盖），账户页解禁导入按钮。
  • 工具脚本对齐：工作区 api-audit.js/list-routes.js 硬编码的 apps/web-vue/apps/api-spring 路径改为 apps/web/apps/server 并参数化，纳入 CI 与 未接入清单.md 联动（比对结果自动刷新台账）。
风险提示：① P1「预订转费用」会改变预算口径（已核销不再计入预估占用），需同步更新 docs/architecture/api-design.md 的预算一节；② 编辑锁表合并涉及存量数据，务必在迁移脚本里做数据搬迁并回滚预案；③ JWT token_valid_after 方案会使改密前签发的 token 全部失效（这正是目的），但需在发布说明中告知用户重新登录；④ 所有新端点沿用 @RequireTripRole/行级权限框架，勿绕过。

05优化后的目标价值流（TO-BE）

预订主线（用户只录一次）
录预订⇢ 凭证自动聚合＋ 定时提醒⇢ 一键转费用⇢ 分摊/结算⇢ 统计（口径统一）
社交主线（有回执）
搜索好友→ 发送请求⇢ 对方收通知→ 同意/拒绝→ 互为好友 · 可私信 · 可见 friends 攻略
一句话总结：这套系统的骨架很好（主链路全通、权限分层、文档齐备），当前的主要损耗不在"功能缺失"而在"数据不流转、入口藏得深"——让预订的金额自动流向费用、让凭证和好友请求长出入口，就是投入产出比最高的四天。
