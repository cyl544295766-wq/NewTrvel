# Travel OS 服务器初始化手册

> 本手册记录生产服务器（Ubuntu 24.04，腾讯云）从裸机到可接收 CI/CD 部署的完整步骤。
> 当前服务器 **已完成初始化**（2026-10-13），本手册用于重建或迁移新服务器时照做。

## 一、基础环境

已验证可用：Java 21（运行 Java 17 构建产物）、Nginx 1.24、Docker + Compose。
缺失时安装：

```bash
sudo apt update
sudo apt install -y openjdk-17-jre-headless nginx docker.io rsync curl
sudo systemctl enable --now docker nginx
```

## 二、部署用户与 SSH

1. 本机生成部署密钥对：`ssh-keygen -t ed25519 -C travel-os-deploy -f travel_os_deploy`
2. 公钥追加到服务器 `/home/ubuntu/.ssh/authorized_keys`，验证密钥可登录
3. 确认 `ubuntu` 免密 sudo（`/etc/sudoers.d/` 中配置 NOPASSWD），CI 重启服务依赖此项

## 三、PostgreSQL（Docker）

国内服务器拉不了 Docker Hub，用腾讯云内网镜像：

```bash
sudo docker pull mirror.ccs.tencentyun.com/library/postgres:16-alpine
sudo docker tag mirror.ccs.tencentyun.com/library/postgres:16-alpine postgres:16-alpine

sudo docker run -d --name travel-os-postgres --restart unless-stopped \
  -e POSTGRES_USER=travel_os \
  -e POSTGRES_PASSWORD=<数据库密码> \
  -e POSTGRES_DB=travel_os \
  -p 127.0.0.1:5432:5432 \
  -v travel_os_pgdata:/var/lib/postgresql/data \
  postgres:16-alpine
```

注意：服务器 6379 已有原生 Redis（本项目不依赖 Redis）；3306 是原生 MySQL（本项目不用）；9000 是 Portainer。

## 四、数据库迁移

迁移脚本统一放在 `apps/server/db/migration/`，命名约定与幂等要求见该目录下的 README。

```bash
# 在仓库根目录打包迁移脚本并上传
tar czf migrations.tar.gz -C apps/server/db migration
scp migrations.tar.gz ubuntu@<服务器>:/tmp/

# 服务器上按文件名顺序执行（首次初始化会跑完整脚本集，建立全部表）
rm -rf /tmp/mig && mkdir -p /tmp/mig
tar xzf /tmp/migrations.tar.gz -C /tmp/mig
for f in $(ls /tmp/mig/migration/*.sql | sort); do
  echo "applying: $f"
  sudo docker exec -i travel-os-postgres psql -U travel_os -d travel_os -v ON_ERROR_STOP=1 -f - < "$f"
done
```

约定：**只增不改，且必须幂等**（`IF NOT EXISTS` / 捕获 `duplicate_object`），
CI 每次部署都会按文件名顺序重放该目录全部脚本。`ALTER TYPE ... ADD VALUE` 不能包在事务里。

## 六、systemd 服务

```bash
sudo cp deploy/systemd/travel-os-api.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now travel-os-api
# 首次需先放 jar：scp travel-os-api-*.jar ubuntu@<服务器>:/opt/travel-os/travel-os-api.jar
systemctl status travel-os-api
curl http://127.0.0.1:3001/api/health/database   # 期望 {"status":"ok","database":"connected"}（APP_PORT=3001；3000 已是 monevo-nginx）
curl -sf http://127.0.0.1:3001/api/health/ready  # 就绪检查：200=库可连+关键表/列齐；503=未就绪（发布验收用）
```

> **unit 内含 `EnvironmentFile=-/opt/travel-os/release.env`**：publish.sh 每次切换会原子重写该文件
> （`TRAVEL_OS_RELEASE_ID=<发布ID>`）并重启，`/api/health` 的 `release` 字段即来自它——用于
> 「运行版本 == 目标版本」核验。unit 的安装/更新由 publish.sh 切换阶段自动完成（daemon-reload），
> 手动初始化时按上面命令执行一次即可。

## 七、Nginx 站点

> 端口约定（2026-11-21 统一）：仓库模板 `deploy/nginx/travel-os.conf` 定位为**生产专用**，
> `listen 8082 default_server` 与生产一致，覆盖后**无需再改端口**；`/api/` 与 `/files/`
> 上游均为 `127.0.0.1:3001`（travel-os-api，`.env` `APP_PORT=3001`）。
> 80 端口归其他项目的整合页（monevo-nginx）；3000 被 monevo-nginx 容器占用，
> **严禁把上游改回 3000**（其 `/api/` 恒 200 会让健康检查假通过）。

```bash
sudo cp deploy/nginx/travel-os.conf /etc/nginx/sites-available/travel-os
sudo ln -sf /etc/nginx/sites-available/travel-os /etc/nginx/sites-enabled/travel-os
# 原 80 端口的 Adminer 站点挪到 8001：
sudo sed -i 's/listen 80;/listen 8001;/' /etc/nginx/sites-available/adminer
sudo nginx -t && sudo systemctl reload nginx
```

> **publish.sh 不包含 Nginx 步骤**：六阶段（构建→备份→jar→迁移→前端→重启+健康检查）
> 只发布应用与静态站，**不会应用或重载 Nginx 配置**。conf 有变更时必须按上面步骤手动
> `cp`（或 `vi` 增量修改）→ `nginx -t` → `systemctl reload nginx`，不会随发布自动生效。

> **受保护文件代理**（2026-11-20，配置已内置）：conf 含 `location ^~ /files/`，把 `/files/**`
> 整体代理到后端（与 `/api/` 同一上游 3001），由 FileController + FileAccessService 做
> Cookie 登录态与对象级授权——图片/PDF 等扩展名的静态规则不会截获它（修复前 `/files/*.png`
> 会被扩展名 location 挡成 nginx 静态 404）。`proxy_pass` 不带 URI，`/files/` 前缀原样转发；
> 不加缓存头、不改写状态码。**服务器上已有的旧版 conf（上游还是 3000 或缺 /files/ 块）需按
> 上面步骤重新应用并 reload 才会生效**，二选一：
> ```bash
> # 方式一（推荐·增量）：只把仓库 conf 里的 `location ^~ /files/ { ... }` 整块插入
> #   服务器现有 /etc/nginx/sites-available/travel-os 的 `location /api/` 之后，
> #   并把两处 proxy_pass 的上游改/确认为 http://127.0.0.1:3001
> vi /etc/nginx/sites-available/travel-os
>
> # 方式二（整体覆盖，模板已与生产一致，无需改端口）：
> sudo cp deploy/nginx/travel-os.conf /etc/nginx/sites-available/travel-os
>
> sudo nginx -t && sudo systemctl reload nginx
> # 快速验证（替换文件名与端口）：
> curl -si http://127.0.0.1:8082/files/<32位hex>.png | head -1     # 未登录应 401（后端 JSON），而非 nginx 静态 404
> curl -si -H 'Range: bytes=0-99' --cookie "access_token=<token>" \
>   http://127.0.0.1:8082/files/<自己的图片>.png | head -1          # 应 206
> ```

## 八、GitHub Actions 与 Secrets

CI（`.github/workflows/ci.yml`）只做构建验证，不再在 Actions 里部署（跨境 scp 直传实测限速 ~40KB/s，
44MB jar 要 25 分钟以上；COS 中转按流量计费已弃用）。**部署统一走本地一键发布 `deploy/publish.sh`**。

> 历史遗留的 `SSH_HOST` / `SSH_PORT` / `SSH_USER` / `SSH_PRIVATE_KEY` / `TENCENT_*` 等 Secrets
> 已无引用，可在仓库 Settings → Secrets and variables → Actions 中清理。

## 九、验证

- `http://<服务器IP>:8082/` 打开前端（80 端口为 Monevo 整合页）
- `http://<服务器IP>:8082/api/health` 返回 ok（含 `release` 字段=最近发布 ID）
- `curl -sf http://<服务器IP>:8082/api/health/ready` 返回 200（库可连+关键结构齐；非 200 即未就绪）
- push 到 main 分支，Actions 中 CI 全绿（后端=临时库迁移+mvn verify，前端=node 测试+分类回归）
- 发布用 `bash deploy/publish.sh`：末尾「发布结果」块三处版本标识一致（health/release.json/
  current-release.txt）即成功；失败场景见 `docs/发布流水线.md` 阶段失败表与人工回滚
